# 기존 사이트를 1.1.0으로 업데이트하기

이 안내는 이미 콘텐츠가 있는 Basic Website CMS 설치를 위한 것입니다. 새로 만드는 사이트는 [첫 실행 체크리스트](FIRST_RUN_CHECKLIST.md)를 사용하세요. [패치노트](../CHANGELOG.md)에서 동작 변경도 확인할 수 있습니다.

## 1. 코드와 데이터의 복구 지점 확보

1. 현재 Git commit·수정 파일·Vercel 배포 ID를 기록합니다. 미커밋 변경을 백업하고, 수정 내용을 무시하는 강제 초기화는 하지 않습니다.
2. Neon의 복구 지점 또는 PostgreSQL 백업을 확보합니다. **별도 테스트 DB에 실제 복원하고 주요 테이블의 행 수와 ID를 비교**합니다. 백업 파일이 존재한다는 사실만으로 복원 검사를 대신하지 마세요.
3. 직접 연결 문자열을 관리자 `.env.local`에 설정합니다. 연결 문자열은 채팅·이슈·PR·Git에 넣지 않습니다. 같은 이름의 셸 환경변수가 있으면 파일보다 우선하므로 대상 DB를 다시 확인합니다.
4. 업그레이드 중에는 관리자 저장 작업을 멈추고, 먼저 복원한 테스트 DB에서 아래 절차를 실행합니다. 고객사마다 다른 구조가 있다면 비교 결과를 검토한 뒤 해당 구조에 맞는 마이그레이션이 필요합니다.

## 2. 새 코드와 의존성 준비

기존 커스터마이즈를 보존하면서 1.1.0 변경을 반영한 다음 저장소 루트에서 실행합니다.

```bash
npm --prefix apps/admin ci
npm --prefix apps/site ci
npm run admin:db:validate
```

Prisma와 seed 명령은 이제 관리자 `.env.local`을 자동으로 읽습니다. 비밀값을 다른 추적 파일에 복사하지 않아도 됩니다. `prisma generate`는 실제 DB를 변경하지 않습니다.

## 3. DB 기준점 등록과 추가 필드 적용

이전 버전이 `db push`로 만들어졌고 Prisma 마이그레이션 이력이 없는 경우입니다. **복원 검사를 끝낸 뒤** 실행하세요.

```bash
npm run admin:db:baseline -- --backup-verified
npm run admin:db:deploy
```

첫 명령은 실제 DB와 이전 버전의 고정 schema를 비교합니다. 일치할 때만 `0_init`을 이미 적용한 기준점으로 등록합니다. 기존 테이블을 다시 만들지 않습니다. 구조 차이 또는 이미 관리 중인 마이그레이션 이력이 있으면 중단하고 해당 설치의 이력을 먼저 검토하세요. 차이를 무시하거나 기준점을 강제로 덮어쓰지 마세요.

두 번째 명령은 `User.googleSubject`(선택적 고유 문자열), `WorkshopRun.revision`(기본값 0인 정수)만 추가합니다. 기존 행·사용자 ID·게시물·일정 ID는 유지합니다. 신규 빈 DB에서는 기준점 명령 없이 `admin:db:deploy`만 실행합니다.

운영 DB에 샘플 seed를 다시 넣거나 `migrate reset`, `db push --accept-data-loss`를 실행하지 마세요. 환경변수가 가리키는 DB는 명령 실행 전에 매번 확인하세요.

## 4. 로그인과 과거 이미지 주소 확인

- 배포 후 기존 관리자 세션은 만료된 것으로 처리됩니다. 관리자에게 다시 로그인하도록 안내합니다.
- 기존 이메일 허용 목록과 manager/editor 역할을 보존합니다. Google 이메일 검증과 고유 식별자가 함께 맞아야 로그인할 수 있습니다. [Google 설정 안내](GOOGLE_OAUTH_SETUP.md)의 Gmail/Workspace 외 이메일 정책을 확인하세요.
- 관리자 도메인을 바꾼 적이 있다면 서버 환경변수 `LEGACY_ADMIN_ORIGINS`에 확인된 이전 origin을 쉼표로 구분해 넣습니다. 예: `https://old-admin.example.com,https://previous-admin.example.com`. 경로·마지막 `/`·와일드카드 없이 정확한 HTTPS origin만 씁니다.
- 이전 도메인의 실제 이미지가 없다면 이 값은 비워 둡니다. 새 주소를 허용한다고 다른 Blob 저장소나 다른 글의 파일에 접근할 수 있게 되지는 않습니다.
- 기존 본문을 일괄 변경할 필요는 없습니다. 호환 읽기를 제공하며, 이후 저장할 때 해당 이미지 주소를 정규화합니다.

## 5. 검사와 두 앱 배포

두 앱 각각의 디렉터리에서 실행합니다.

```bash
npm audit --audit-level=high
npm run lint
npm run typecheck
npm test
npm run build
```

로컬 DB 통합 검사를 실행하려면 전용 PostgreSQL을 준비하고 `CMS_TEST_DATABASE_URL`을 별도로 설정하세요. 테스트는 `127.0.0.1` 또는 `localhost`의 `cms_test`/`ci` DB만 허용합니다. 운영 DB 연결 문자열을 이 변수에 넣지 마세요. 기본 테스트 실행에서 이 변수가 없으면 DB 통합 검사만 건너뛰며, 검사하지 않은 항목을 성공으로 보고하지 않습니다. 공개 CI는 임시 PostgreSQL에서 통합 검사도 실행합니다.

마이그레이션이 적용된 뒤 관리자와 공개 사이트를 각각 배포합니다. Vercel에서 자동 배포가 켜져 있다면 DB 준비 전에 새 코드가 먼저 배포되지 않도록 전환 순서를 관리하세요.

## 6. 실제 주소에서 확인하기

- Google 재로그인, 기존 사용자 별명·작성자·manager/editor 권한.
- 기존 글·일정·첨부와 본문 이미지 표시. 과거 관리자 주소의 이미지도 표본을 확인합니다.
- 같은 일정을 두 탭으로 열어 A 저장 뒤 B 저장이 충돌로 거부되고 B의 입력이 유지되는지 확인합니다.
- 모집 기간 공백과 수업 종료 시각의 상태 표시.
- 글 공개→비공개/삭제 뒤 기존 파일 URL이 계속 공개되지 않는지 확인합니다.
- PC·모바일 화면과 콘솔 오류. 기본 디자인 변경은 이 업데이트의 목적이 아닙니다.

## 7. 문제가 생기면

검증 실패 상태로 추가 배포나 정리를 진행하지 않습니다. 우선 이전 정상 Vercel 배포로 되돌립니다. 이번 필드는 추가 방식이므로 이전 앱이 동작하도록 추가 필드를 남겨 두고 원인을 조사합니다. 필드를 제거하거나 운영 데이터를 재시딩하는 방식으로 되돌리지 마세요. 데이터 손상이 확인되면 복원 검사한 백업과 작업 기록을 기준으로 복구합니다.

사용하지 않는 업로드 파일은 다음 명령으로 **후보만** 조사할 수 있습니다.

```bash
npm run admin:files:inventory -- --dry-run
```

이 명령에는 삭제 옵션이 없습니다. 출력은 비공개 운영 자료로 보관하고 Git에 넣지 마세요.
